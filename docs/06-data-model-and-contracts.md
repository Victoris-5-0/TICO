## Shared public schema

`client/prisma/schema.prisma` is the single source of truth for every table below. All tables live in PostgreSQL's shared `public` schema. Prisma alone creates migrations; the Python service keeps synchronous SQLAlchemy mappings aligned for the tables it reads and writes.

### Game aggregates

| Aggregate | Important fields and invariants |
| --- | --- |
| `User` / `StudentProfile` | Better Auth owns the user identity plus `auth_accounts` and `auth_sessions`; role and XP live on `users`. Locale, coarse age band, onboarding completion, and the self-reported Learner/Challenger preference live in `student_profiles`. |
| `World` / `Lesson` | fixed chapter and linear `sequenceOrder`; lesson has `isSkippable` |
| `Concept` / `LevelConcept` | concept order; exactly one primary concept per lesson; carried weights 0–1 |
| `Mission` | stable identity attached to one lesson and world |
| `MissionVersion` | immutable payload after publication; locale content, starter variants, tests, solution, manifest version |
| `Asset` / `MissionAsset` | stable manifest ID, kind, storage object, dimensions, locale-neutral alt intent |
| `MissionSession` | learner, mission version, scaffold plan, state, timestamps |
| `CodeSubmission` | session, monotonically increasing attempt, phase, code, result, timing, prior hints |
| `UserProgress` | unique learner + lesson; state and first completion timestamp |
| `CompanionThread` / `Message` | mission-bounded conversation with safety metadata |
| `ContentReview` | reviewer, version, decision, notes, timestamp |

Published `MissionVersion` rows are immutable. Publishing atomically changes the stable mission's active version. Submissions keep their exact version; progress belongs to the stable lesson/mission identity.

### AI capability tables

The target Prisma schema will define these eight launch tables in `public`; they are not a separate schema. They are a design contract until the corresponding Prisma migration exists:

- `ai_interaction`
- `concept_mastery`
- `student_lesson_plan`
- `mission_session`
- `hint_event`
- `mission_template`
- `generated_mission`
- `student_profile`

`ai_interaction` is implemented first and records capability, prompt version, model, token counts, estimated cost, latency, outcome, safety result, and trace ID. It must not store email, name, OAuth data, or raw secrets.

The FastAPI service never runs DDL and has no Alembic history. A schema change is made in Prisma, committed with its Prisma migration, and followed by an update to the corresponding SQLAlchemy mapping and cross-service contract fixture. Use explicit snake-case mappings on Prisma models and fields so both ORMs address the same identifiers.

Worker messages are discriminated, versioned, and parsed before use. See the runner document for execution rules.

## AI HTTP envelope

All `/v1` requests include `X-Request-ID`; retryable commands also include `Idempotency-Key`. Success bodies contain `data` and `meta`; errors use:

```json
{
  "error": {
    "code": "manifest_reference_invalid",
    "message": "A safe user-facing explanation",
    "request_id": "01J...",
    "retryable": false,
    "details": {}
  }
}
```

Never put secrets, code solutions, or stack traces in a browser-facing error.

## Endpoint order and contracts

| Order | Endpoint | Core input | Core output |
| ---: | --- | --- | --- |
| 1 | `POST /v1/hints` | mission/session IDs, code excerpt, last result, locale | fixed rung, safe hint, cached flag |
| 2 | `POST /v1/submissions/analyze` | normalized failure evidence | fixed error category, confidence, feedback key |
| 3 | `POST /v1/students/{id}/refresh` | evidence watermark | mastery deltas and reason |
| 4 | `POST /v1/students/{id}/plan` | diagnostic/version | ordered required/optional lesson decisions |
| 5 | `POST /v1/missions/next` | learner profile, lesson, world manifest version | validated mission or template fallback |
| 6 | `POST /v1/tico/messages` | mission thread, message, locale | SSE text deltas then completion metadata |
| 7 | `POST /v1/challenges/next` | mastered concept snapshot | validated mixed challenge |

The server derives `student_id`, role, allowed lesson, hint rung, and legal manifest choices. Clients cannot choose them.

## Mission DTO

A generated mission includes stable/version IDs, prompt version, locale strings, scene and character IDs, prop bindings, target/carried concepts, scaffold plan, execution mode, starter code, visible cases, private tests, reference solution, four hint intents, success/failure reaction IDs, and validation report.

The generator never emits raw image URLs or invented prop methods. It emits manifest IDs; the client resolves approved assets.

## Atomic completion

Within one Prisma transaction:

1. Insert the submission using unique `(sessionId, attemptNumber)` or supplied idempotency key.
2. If it passed, upsert progress without overwriting an earlier completion time.
3. Award the first-completion 100 XP only if no prior award exists.
4. Award extension 25 XP only once.
5. Add an outbox event for asynchronous mastery refresh.

Retries return the original result and never duplicate XP or events.

## Versioning

- HTTP breaking changes require `/v2`; additive optional fields do not.
- Every mission stores curriculum, prompt, manifest, and validator versions.
- Every mastery record stores formula version.
- Every model interaction stores the actual routed model ID.
- Consumers ignore unknown additive fields and reject unsupported major contract versions.
