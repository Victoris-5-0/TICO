Section 01

Where the AI service starts and stops

The single most important thing to agree on before anyone writes code: this service returns JSON decisions and nothing else. It never renders game state, never executes student code, and never owns a game table.

Next.js on Vercel owns the UI, the game engine, the code editor and code execution. It reads plain game data straight from Supabase under row-level security. It calls tico-ai when it needs a judgement or a mission.

Decide this once, write it down

FastAPI holds the service-role key and therefore bypasses row-level security entirely. Every endpoint must confirm that the user_id in the verified JWT actually owns the session or student it is being asked about. Miss this and any logged-in student can read another student's data by changing an ID.

Section 02

The learning model

Every design decision below follows from these six properties.

1. The concept order is fixed

Programming is learned in order — variables, then conditions, then loops, then functions. The system never reorders concepts, and there is no prerequisite graph to traverse.

2. But which lessons a student needs is not fixed

An experienced student may already know loops. Forcing them through every loops lesson to reach functions wastes exactly the students you most want to keep. So after the diagnostic, each lesson is marked required or optional for that student, and their path is the fixed sequence minus what they have proven they don't need. The order never changes; the membership does. That is a filter over an ordered list, not a graph traversal.

3. Learning is cumulative — target and carried concepts

Concepts do not disappear once taught. A loops mission still uses variables and conditions. So every lesson has a target concept (the new thing) and a set of carried concepts (already learned, exercised again).

This lives in exercise_concepts with is_primary and weight. It is the most load-bearing join in the schema: it tells the system what a mission touches and how much each result should move each concept's mastery. It also keeps early concepts alive — a student who learned variables in week one keeps being assessed on them, without a single extra mission.

4. Worlds are chapters spanning several lessons

LessonsWorldTarget conceptCarried
1–3Cairo MetroVariables—
4–6Cairo MetroConditionalsvariables
7–9Cairo TrafficLoopsvariables, conditionals
10–12Nile / farmingFunctionsall three

Twelve lessons, four concepts, three worlds for the MVP. The world changes less often than the concept does, so a map gets several lessons before the student leaves it.

5. Adaptation happens inside a lesson

Not which concept, not which world — both fixed. Adaptation has three levers: how much of the carried concepts is pre-scaffolded in the starter code, how many reps before moving on, and advance or hold at the concept gate.

6. After the roadmap: the challenge arena

Students who finish enter Challenges — tasks across every mastered concept, mixed, with no scaffolding and a shorter hint ladder. Already in the product's IA: the landing page has a Challenges nav item. It is also where generated variety matters most, because there is no lesson order to fall back on.

Every one of them writes a row to ai_interactions — capability, model, tokens, cost, latency. That single table is how you answer “what did the AI do, and what did it cost” with a query instead of a slide.

Where the model is deliberately not called

  • Mastery numbers. Pure Python. A model producing 0.73 is nonsense — slower, costlier, and different every call.
  • Which hint rung. Counted from hint_events in Python before the model is asked for anything. That is precisely why TICO cannot skip to the answer: it was never asked for the answer.
  • The next lesson. sequence_order + 1. A sort, not a decision.
  • Scaffold plan and advance-or-hold. A rule — unless the evidence conflicts, which is call 7.
  • Whether a generated mission is valid. A Python validator re-reads the world manifest. Never the model saying its own output is fine.
  • Achievements and XP. Deterministic criteria evaluated in code.

Nour plays Cairo Metro, lesson 4 — conditionals, carrying variables.

Nine steps, five model calls — and one of those was free, because the cache had already answered that mistake for another student.

There are only two shapes of call

Write prose (1, 2, 3, 8) — the model is told exactly what to say and how much. It is a writer, not a decider. Make a bounded judgement (4, 5, 6, 7) — one family from seven, a scene from the manifest, skip or don't skip. Python then validates that the answer is in the set and rejects it if not. There is no third kind: nothing in TICO hands a model an open question and trusts the reply.

Section 05

Rules propose, the model reviews

Two of the six services — the planner and the composer — make decisions about a student rather than writing text for one. Those decisions follow the same pattern, and it is worth stating once because it is the answer to “where exactly is the AI here?”

A threshold rule is fast, reproducible, free and explainable — but it is equally confident whether the evidence is clear or contradictory. A student with high accuracy and heavy hint use is genuinely ambiguous, and a rule just picks a side. So:

Where this applies, and where it does not

Planner: a rule proposes required/optional per lesson; the model reviews every skip, because skipping on the evidence of one short diagnostic is inherently low-confidence. Composer: a rule sets the scaffold plan and the advance/hold call; the model reviews only when the profile is contradictory. Mastery numbers are never model-produced — the inputs are counts and the output is a float, which is the one shape where a model is strictly worse: slower, costlier, and different every call.

Section 06

How a mission gets made

Creating the mission and adapting it are one pipeline, not two. The plan says which lesson is next for this student; the composer says how hard and how much help; generation composes the scenario from the inventory against those parameters.

The world inventory

Each world is one manifest listing everything a mission there may use: scenes, characters, props, mechanics, and what may vary. If it is not in the file, the AI cannot put it in a mission — generation is selection from a closed set, never invention.

props:
  - id: gate
    states: [open, closed]
    verbs:
      - "gate.open()"
      - "gate.close()"

  - id: passenger_counter
    reads:
      - "station.passengers  -> int"

constraints:
  may_vary:     [scene, params, brief_wording, npc_lines, carried_scaffold]
  may_not_vary: [world, target_concept, mechanic, prop_verbs, solution_shape]

The verbs and reads lists are the important part: they are the actual code API the student writes against. If the model invents gate.unlock() and the engine only implements gate.open(), the mission is unsolvable. Listing them lets the validator catch that before it ships. The asset catalogue and the game API are the same document. A worked example is at content/worlds/cairo_metro.yaml.

What varies, and what adaptation changes

Same world, same target concept, same mechanic — three missions:

Section 08

The contract with the client

The Next.js team cannot build a hint panel against an endpoint that does not exist yet. Built milestone by milestone, the first working call to /v1/missions/next lands on 13 September — two days before the deadline, on the same days it is being written. That is how you end up with a backend that works and a screen that does not.

The fix

Ship the contract on day two, not the implementation. All seven endpoints exist by 5 September, validating input properly and returning realistic hard-coded data shaped exactly like the real thing. Each stub is then replaced as its milestone lands. The shapes never change — only the behaviour behind them.

EndpointStub liveReal behaviour
POST /v1/hints5 Sep9 Sep
POST /v1/submissions/analyze5 Sep10 Sep
POST /v1/students/{id}/refresh5 Sep11 Sep
POST /v1/students/{id}/plan5 Sep12 Sep
POST /v1/missions/next5 Sep13 Sep
POST /v1/tico/messages5 Sep14 Sep
POST /v1/challenges/next5 Sep15 Sep

The client gets nine days of integration instead of two, and the stubs cost two or three hours because the Pydantic contracts already exist.

What the client team gets, and when

  • 6 Sep — a live URL. The EC2 deploy already scheduled for that day carries the whole stubbed API, not just /health.
  • Typed calls, generated not hand-written. FastAPI publishes /openapi.json, so the client runs npx openapi-typescript <url>/openapi.json -o client/src/lib/ai-api.d.ts and gets types that cannot drift from this service.
  • Interactive docs at /docs — every endpoint, every field, every enum value, with a Try It button.
  • The auth story: which header, which token, what a 401 looks like.
  • A warning that TICO chat is SSE, not JSON. That is real frontend work — an EventSource or a streaming fetch reader, not await res.json(). Discovering it on the 14th would be brutal.

Two integration checkpoints

Half an hour each, with whoever owns the Next.js side. Not a status meeting — sit together and make one screen work end to end.

WhenWhat
10 Sep · after M2The hint panel calls the real /v1/hints and TICO's words appear on screen.
13 Sep · after M5The mission map calls the real /v1/missions/next and a generated mission renders.

Contract freeze

Shapes are stable from 5 September. If one genuinely has to change, tell the client team before pushing it — a silent field rename costs them more than it costs you, and there is no slack left in either schedule to absorb it.

Section 09

The database

The database already exists. Migration 20260902000000_init ran on 2 September and the seed populated it — users, tracks, lessons, exercises, submissions, user_progress, companion_chats. It is a competent generic coding-LMS schema. Its problem is that it records outcomes, and adaptive AI runs on evidence.

The one-sentence version

user_progress tells you a student finished lesson 7. It cannot tell you they took four attempts, burned hints 1 through 4, kept writing = instead of ==, and are shaky on conditionals but fine on loops. The second sentence is the student model. It is the product.

Deliberately not built

  • A prerequisite table. The concept order is a sort column, not a graph. Per-student variation lives in lesson_plans.
  • pgvector / RAG. Not enough content volume to beat the manifest and SQL filters.
  • A second chat table. companion_chats already exists; LangGraph keeps working state in its own schema.
  • A leaderboard table. A query over users.xp with a LIMIT.
  • An asset table. The world manifest is already the asset catalogue.

Migrations — Prisma owns the schema

client/prisma/schema.prisma is the single source of truth for every table, the AI ones included, exactly as the root AGENTS.md requires. This service runs no Alembic — SQLAlchemy maps to tables it did not create. Adding a table means editing schema.prisma and running pnpm db:migrate from client/.

Never run prisma migrate reset against the shared database. It uses DROP CASCADE and wipes everyone's data, and Prisma offers it whenever it detects drift. Announce every migration before pushing it — one shared database means yours is everyone's the moment it lands.

Stack and deployment

Tooling and deployment follow Sanjeev Thiyagarajan's FastAPI course. Three things had to change; each is deliberate.

  1. Pydantic v2, not v1. LangChain and LangGraph require it. The one thing that cannot be copied.
  2. Verify JWTs, don't issue them. The course's oauth2.py is dropped. Unconfirmed: this assumes Supabase Auth; if the client issues its own sessions over Prisma, the verification changes shape.
  3. No Heroku. Free tier is gone and the architecture diagram says AWS — so the course's Ubuntu VM recipe runs on EC2.
  4. No Alembic. The course migrates with Alembic; this repo migrates with Prisma from client/, because the monorepo already has one source of truth and two migration tools on one database is the fastest way to lose it. SQLAlchemy stays for reads and writes.

A bonus from following the course exactly

Sticking with synchronous SQLAlchemy and psycopg2 removes a whole class of problem: the asyncpg prepared-statement failure against Supabase's pgbouncer pooler simply does not apply. Deploy FastAPI on EC2 rather than Vercel — Python serverless plus long SSE streams plus LangGraph checkpoints is a bad combination.

Safety, because the users are 10 to 17

  • Every model output crosses a Pydantic model. Invalid → retry once → authored fallback. A child mid-mission never sees a 500.
  • Moderate free text the student types before it enters a prompt; record the verdict on ai_interactions.
  • No complete solution before the final hint rung. Asserted in tests, not trusted to a prompt.
  • Pass locale explicitly — TICO speaks Egyptian Arabic, code identifiers stay English.
  • A generated mission is never shown unvalidated. Rejected twice → fall back to template defaults.
  • A lesson marked skippable can always be replayed. Skipping is a suggestion, never a lock-out.

The eval suite — 30 to 50 cases, in CI

  • Hint leak test. Early rungs contain no identifier from the solution. Pure string assertion.
  • Generation legality. Every generated mission references only ids and verbs in the manifest, and its solution passes its own tests.
  • Classifier accuracy. 30 hand-labelled wrong submissions, measured and tracked.
  • Planner safety. Synthetic diagnostics in; assert no lesson is skipped when its concept mastery is below threshold, and that is_skippable = false lessons are never optional.
  • Composer sanity. Assert a weak carried concept is never scaffolded away entirely.

Settled: the language is Python

Student code is Python, so manifest verbs are Python (gate.open(), station.passengers -> int), starter code is Python, and hint prose uses Python terms — = versus ==, indentation, if/elif. The Figma mockup showing JavaScript is superseded.

The hint ladder — 4 rungs

The server counts prior hint_events rows and fixes the rung in rules/hint_ladder.py before any model is called. The model writes prose for that rung only. Worked on the most common Python beginner error, = instead of ==:

RungJobTICO says
1Orient“The gate never opens. Look carefully at the line where you check the passengers.”
2Question“In Python, what is the difference between = and ==? What is your condition trying to do?”
3Name it, show a foreign example“This is assignment versus comparison. Comparing looks like if age == 12:”
4Walk to the fix, in words“Your condition should compare, not store. Change the single = in that line to ==.”

No rung ever emits a complete solution. After rung 4 the student goes to a mini-practice on that one idea and then returns to the mission — exactly what the team's UX flow already showed. It also makes the claim “TICO never hands over the answer” literally true, which is a stronger thing to say to a judge than “not until the last hint”.

The leak test is graded by rung: rungs 1–2 contain no identifier from the solution, rung 3 contains none of the student's target values, and rung 4 contains no complete runnable line.

Classifying a wrong answer — family and tag

A closed enum alone is too narrow. Beginners make contextual mistakes that a fixed taxonomy dumps into unknown, and an unknown produces a useless hint. Free text alone is worse: it breaks the hint cache, because free text is never equal twice, and it breaks the mastery counts, because you cannot count prose. So the classifier returns both.

FieldKindWhat it is for
familyClosed enum · 7 valuessyntax · name · type · logic · incomplete · runtime · unknown. Coarse and stable. Drives syntax_vs_logic and the classifier eval.
tagOpen snake_casee.g. assignment_vs_comparison. The hint cache key, and specific enough for a genuinely good hint.
misconceptionFree proseOne sentence naming what the student misunderstands. Goes into TICO's next hint.

The prompt carries the list of tags seen so far and tells the model to reuse one if it fits, otherwise coin a new one. A small error_tag table keeps tag, family, first-seen and count, so the vocabulary grows from real students rather than being guessed in advance. A spike in new tags is a signal to go and look.

This removes a blocker

“Agree a fixed error-category enum” was on the waiting-on-the-game-developer list and blocked M3. With an open tag vocabulary it is not blocked on anyone — ship with an empty tag list and it fills itself. Constrain the shape, not the vocabulary.

  • Avoid gemini-2.5-* — retiring 20 October 2026. That is after your deadline, but there is no reason to start on a retiring model.
  • with_structured_output() accepts Pydantic models directly, which is exactly what guards.py needs.

One consequence of choosing Gemini

Prompt caching will not carry the cost story here. Gemini's context caching is built for large contexts and carries minimum-token thresholds; TICO's hint prompts are short and will not reach them. That promotes the Postgres hint cache from an optimisation to a requirement — it is now the primary cost lever, and the reason beginners failing in identical ways is such a useful property. Also check the rate limit on whichever tier the key sits on: a per-minute cap tripping mid-demo is indistinguishable from a broken service.
