TICO · Code Egypt · AI backend

Six services, seven use cases

One specification per thing a student actually does: who triggers it, what must already be true, what happens step by step, what goes wrong, and what it leaves behind in the database. Written so each can be built and tested without reading the others.

Section 01

Services and actors

Nine proposed services collapsed into six. TICO is the mascot, the hint-giver and every in-world voice, so hinting, coaching and NPC dialogue are one service.

Rules propose, the model reviews

The planner and the composer decide things about a student rather than writing text for one. Both follow the same pattern: a pure-Python rule produces a decision and a confidence; when the evidence conflicts, a model reviews the full profile and confirms or overrides it with a written reason. Clear-cut cases never reach a model, so the system stays cheap and reproducible — and because decided_by and reason are logged, every decision is auditable. Mastery numbers are the exception: always Python, never a model.

Only one actor is a person. That distinction matters: most calls come from the game engine or a background job, and a use case that assumes a human is waiting gets designed with the wrong latency budget.

ActorKindRole
StudentPerson, 10–17The only human actor. Asks TICO for help, submits code, finishes missions.

Session workerSystem — backgroundFires after a session closes. Nobody is waiting, so it may be slow.
Content authorPerson, your teamWrites the world manifests. Never appears at runtime, but bounds everything generation may invent.

Section 03

The seven use cases

UC-01Place a new student and build their pathservices/planner.py + domain/plan.py
Primary actor
Student
Trigger
Finishes onboarding questions
Endpoint
POST /v1/students/{id}/plan
Model call
Reviews every skip
Preconditions
  • The student has an account and a verified JWT.
  • They answered onboarding, including whether they already know programming.
  • Every lesson carries is_skippable — some must never be optional.
Main flow — beginner
  1. Student says they are new to programming.
  2. Mark every lesson required. No diagnostic, no model call.
  3. Seed student_profile with a low confidence.
Main flow — claims experience
  1. Serve one diagnostic mission touching all four MVP concepts lightly.
  2. Observe: solved or not, attempts, hints used, error categories, time.
  3. domain/plan.py proposes required or optional for each lesson — a threshold on the demonstrated mastery of that lesson's target concept. Pure Python, with a confidence.
  4. For every lesson the rule wants to mark optional, a model reviews the full diagnostic and confirms or overrides. Skipping on one short diagnostic is inherently low-confidence, so every skip gets reviewed — not just the ambiguous ones.
  5. Write one student_lesson_plan row per lesson, with reason and decided_by.
  6. One model call writes the friendly summary: what they are skipping and why.
Exceptions
  • Skipped onboarding. Everything required. Nothing is lost; UC-06 will re-plan as evidence accumulates.
  • Abandoned the diagnostic. Treat as a beginner signal — everything required.
  • Rule wants to skip an is_skippable = false lesson. Refuse before the model is even called.
  • Model disagrees with the rule. The model wins, and the disagreement is logged — a run of these means the threshold is wrong.
Postconditions
writes → student_lesson_plan (one row per lesson) · student_profile · ai_interaction

The order never changes — only which lessons are in the path. A skipped lesson stays replayable: skipping is a suggestion, never a lock-out. Self-reported level is a weak prior; set confidence low so two real sessions can override it.

UC-02Start the next missiondomain/composer.py + ai/graphs/mission_gen.py
Primary actor
Student
Trigger
Opens the map, or finishes a mission
Endpoint
POST /v1/missions/next
Model call
1–3 · validated
Preconditions
  • A student_lesson_plan exists for this student (UC-01).
  • A world manifest exists for the world that lesson lives in.
  • level_concept records the target and carried concepts for that lesson.
Main flow
  1. Lesson plan returns the next lesson still marked required, skipping any marked optional. Fixed order, a SQL read, no decision.
  2. Student model supplies mastery on the target concept and on each carried concept.
  3. Composer computes, in pure Python: the scaffold plan per carried concept, difficulty parameters, whether this is a first attempt or an extra rep.
  4. Generation reads the world manifest and composes a scenario against those parameters — scene, characters, brief, starter code, solution, tests.
  5. Validator re-reads the manifest and rejects anything referencing a scene, prop or verb that does not exist; runs the solution against the tests.
  6. Invalid → feed errors back and regenerate. At most two repairs.
  7. Persist generated_mission with validated = true, and return it.
Exceptions
  • Still invalid after two repairs. Fall back to the template's default parameters. The student gets a working mission, never an error.
  • An equivalent mission was already generated for this template, params and scaffold plan. Reuse the row — a direct cost saving.
  • Roadmap complete. Route to the challenge arena (UC-07).
Postconditions
writes → generated_mission · mission_session (opened) · ai_interaction

This one call is the whole create-and-adapt pipeline. The world and the target concept were fixed before it started; what the model contributed was the situation, chosen from the manifest.

UC-03Ask TICO for a hintai/chains/tico_hint.py
Primary actor
Student
Trigger
Asks for help, or stalls past a threshold
Endpoint
POST /v1/hints
Model call
Yes · cached
Preconditions
  • An open mission_session exists and the JWT owner owns it.
  • Prior hint_event rows determine which rung comes next.
Main flow
  1. Count prior hint events for this session and concept.
  2. domain/hint_ladder.py decides rung N — pure Python, before any model is involved.
  3. Look up the cache on (level_id, rung, error_category, scaffold_state).
  4. On a miss, the model writes the prose for rung N only, in TICO's voice. It is never shown the solution.
  5. Guard validates the shape and asserts no solution identifier appears in early rungs.
  6. Write hint_event; return the hint with an is_final flag.
Exceptions
  • Ladder exhausted. Return the final authored explanation and mark the session fully hinted — strong evidence for UC-06.
  • Leak assertion fails. Discard the output, serve the authored hint for that rung, log a prompt regression.
  • Daily call cap hit. Serve cached or authored hints only.
Postconditions
writes → hint_event · hint cache · ai_interaction

If the composer scaffolded a carried concept away, TICO must not hint about it — the scaffold state is part of the prompt and the cache key.

UC-04Ask TICO a questionai/graphs/tico_chat.py
Primary actor
Student
Trigger
Types a message to TICO
Endpoint
POST /v1/tico/messages · SSE
Model call
Yes · streaming
Preconditions
  • An open mission_session — it supplies the LangGraph thread_id.
  • TICO's persona and the mixed-language rule are in the system prompt.
Main flow
  1. Moderate the student's text before it enters any prompt.
  2. Load conversation state from the Postgres checkpointer, keyed on the session id.
  3. Build the prompt stable-first: persona, then mission, then profile, then — last — the message.
  4. Stream the reply over SSE.
  5. Checkpoint the new state; log the call.
Exceptions
  • Moderation flags the input. A gentle in-character redirect. Record the verdict. Never send the text to a model.
  • Student asks outright for the answer. TICO refuses in character and offers the next hint rung instead.
  • Session closed. Reject — TICO has no context to stand on.
Postconditions
writes → langgraph checkpoints · ai_interaction (with moderation_flag)

Same character and same persona as UC-03. What differs is only state and streaming — which is why these are one service, not two.

UC-05Submit code that failsai/chains/classify_error.py
Primary actor
Student
Trigger
Runs code that does not pass its tests
Endpoint
POST /v1/submissions/analyze
Model call
Yes · structured
Preconditions
  • The game engine has already executed the code and holds the real failure output.
  • A fixed error-category enum is agreed with the game team.
Main flow
  1. Receive the code, the runtime error and the failing expectation.
  2. Model classifies it into one category from the fixed enum and names the misconception in a sentence.
  3. Guard rejects any category outside the enum.
  4. Write error_category onto code_submission.
  5. Return it — it becomes part of the hint cache key in UC-03 and evidence in UC-06.
Exceptions
  • Low confidence. Escalate once to a stronger model; if still unclear, label unknown and continue.
  • Code empty or unchanged from the starter. Skip the model — that is a stalling signal, not an error.
  • The error is in a scaffolded region. Flag it: the composer scaffolded something the student still broke, which is useful signal about the scaffold itself.
Postconditions
writes → code_submission.error_category · ai_interaction

The AI service never runs the student's code. It receives execution results and reasons about them. That boundary is what keeps the platform deterministic.

UC-06Finish a missionservices/student_model.py
Primary actor
Session worker
Trigger
A mission_session closes
Endpoint
POST /v1/students/{id}/refresh
Model call
None for the numbers
Preconditions
  • The session is closed, with submissions and hint events attached.
  • level_concept gives the weight of each concept in that mission.
Main flow
  1. Gather every piece of evidence: attempts, hints, error categories, timings.
  2. domain/mastery.py updates mastery for the target concept at full weight and each carried concept at its own weight — pure Python.
  3. Upsert concept_mastery.
  4. Recompute hint_dependency, syntax_vs_logic, pace, skill_band.
  5. Composer decides advance or hold. The rule compares mastery to the gate threshold. If the evidence conflicts — solved it but leaned on every hint, or fast but three failed attempts — a model reviews the profile and confirms or overrides, with a reason.
  6. Planner re-plans forward. Real evidence is better than a diagnostic, so lessons still marked optional can be flipped back to required if mastery came out weaker than the skip assumed.
  7. Optionally one model call writes the human-readable summary after the numbers exist.
Exceptions
  • Session abandoned with no submissions. Record the abandonment — quitting is evidence — but do not move mastery.
  • Job fails. Retry. The profile is a cache; a stale one degrades quality but does not break the request path.
  • Re-plan would un-skip a lesson the student already passed. Leave it — never send someone backwards through completed work.
Postconditions
writes → concept_mastery (target + carried) · student_lesson_plan (re-planned) · student_profile · ai_interaction

Step 2 is where cumulative learning pays off. A student who learned variables in week one keeps being assessed on them every time a later mission carries them — without a single extra mission being built.

UC-07Enter the challenge arenadomain/composer.py + ai/graphs/mission_gen.py
Primary actor
Student
Trigger
Opens Challenges, having finished the roadmap
Endpoint
POST /v1/challenges/next
Model call
Yes · validated
Preconditions
  • The student has mastered at least two concepts.
Main flow
  1. Select the mastered concepts, weighted toward the weakest — a challenge should stretch, not flatter.
  2. Composer sets: no scaffolding, a shorter hint ladder, a higher difficulty band.
  3. Generation composes a scenario mixing those concepts, in any world the student has visited.
  4. Validator checks it as in UC-02.
  5. Return the challenge; record the result against every concept it touched.
Exceptions
  • Fewer than two concepts mastered. Keep Challenges locked and say why.
  • Repeated failure. Drop the difficulty band rather than reintroducing scaffolding — the arena's whole point is that there is none.
Postconditions
writes → generated_mission · mission_session · concept_mastery · ai_interaction

This is where generation matters most: there is no fixed lesson order to fall back on, so every challenge has to be composed. It is also the only place a mission may mix worlds.

One student, one mission, end to end

Nour is 13, in Grade 8 in Mansoura. She is at lesson 4 — conditionals, in Cairo Metro, carrying variables. Her mastery on variables is shaky, so nothing gets scaffolded away.

Two things this table is showing

First: the session close writes two mastery rows, not one. Conditionals at full weight, variables at carried weight — Nour practised both, so both move. Second: her next mission is the same world with a different situation. Cairo Metro didn't change, the if mechanic didn't change; the scene, the numbers and the story did. That is what generation produces.

Both assumptions are now settled

UC-03 runs a 4-rung ladder: orient, question, name the concept with a foreign example, then walk to the fix in words. No rung emits a complete solution, so the “ladder exhausted” path leads to a mini-practice rather than the answer. UC-05 assumes the engine executes Python and returns results — which also fixes the verbs in every world manifest as Python (gate.open(), station.passengers -> int). Every model call routes through Gemini via ai/router.py.
